Создайте файл `UPCOMING_CHANGELOG.md` на основе структурированного списка изменений, представленного ниже.
Если файл `UPCOMING_CHANGELOG.md` уже существует, полностью игнорируйте его текущее содержимое.
Не сохраняйте, не объединяйте и не используйте повторно текст из существующего файла.

Входные данные уже содержат точный диапазон коммитов с момента последнего релиза, не являющегося черновиком.
Коммиты уже отфильтрованы по пакетам, относящимся к релизу, и сгруппированы в
разделы релизов. Не загружайте релизы GitHub, запросы на слияние или не создавайте собственный список коммитов.
Входные данные также могут включать раздел `## Ввод данных от участников сообщества`.

Перед записью каких-либо изменений проверьте реальное различие с помощью команд `git show --stat --format='' <hash>` или `git show --format='' <hash>`, чтобы понять фактические изменения кода, а не только сообщение коммита (оно может вводить в заблуждение).

При определении авторства не используйте `git log` или метаданные автора.

Правила:

- Запишите итоговый файл с разделами в следующем порядке:

## Core`, `## TUI`, `## Desktop`, `## SDK`, `## Extensions`
- Включайте только разделы, содержащие хотя бы одну важную запись
- Сохраняйте один пункт на каждый сохраненный коммит
- Пропускайте коммиты, которые являются полностью внутренними, CI, тестами, рефакторингом или иным образом не ориентированы на пользователя
- Начинайте каждый пункт с заглавной буквы
- Отдавайте предпочтение изменениям для пользователей, а не изменениям кода внутри
- Не копируйте необработанные префиксы коммитов, такие как `fix:` или `feat:`, или номера PR в конце, такие как `(#123)`
- Атрибуция сообщества детерминирована: сохраняйте только существующий суффикс `(@username)` из входного файла changelog
- Если у входного пункта нет суффикса `(@username)`, не добавляйте его
- Никогда не добавляйте новый суффикс `(@username)` из `git show`, авторов коммитов, имен или адресов электронной почты
- Если Если не осталось значимых записей и нет блока участников, напишите ровно «Значимых изменений нет».
- Если не осталось значимых записей, но есть блок участников, пропустите все разделы релиза и верните только блок участников.
- Если входные данные содержат «## Ввод данных от участников сообщества», добавьте блок ниже этого заголовка в конец итогового файла без изменений.
- Не добавляйте, не удаляйте, не переписывайте и не меняйте порядок имен участников или заголовков коммитов в этом блоке.
- Не выводите раздел благодарности из основных пунктов сводки.
- Не включайте заголовок «## Ввод данных от участников сообщества» в итоговый файл.
- Сосредоточьтесь на написании как можно меньшего количества слов, чтобы донести свою мысль — пользователи будут бегло просматривать список изменений, поэтому мы должны быть точными.

**Важно отметить, что список изменений предназначен для пользователей (которые хотя бы немного разбираются в технике), они могут использовать TUI, Desktop, SDK, плагины и так далее. Будьте внимательны при понимании того, как последствия могут быть не сразу очевидны. Например: Обновление пакета выглядит как внутреннее, но может исправить ошибку. Или рефакторинг может также стабилизировать состояние гонки, исправляя ошибки для пользователей. Заголовок/тело запроса на слияние + сообщение коммита дадут вам контекст автора, обычно содержащий результат, а не только технические детали**
